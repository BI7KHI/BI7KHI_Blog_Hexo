## 前情提要

上回把一辆山地车塞进了 48V 后驱电机、大疆 TB47/TB78 电池和恒泰普瑞（HTPR）控制器。车能跑，但有一件事一直很难受：

**控制它的唯一入口是厂商的微信小程序。**

小程序本身没毛病，能连、能看、能改参数，但它有三个致命问题：

* 数据**只能看，不能留存**，没有历史曲线；
* 没有原始帧、没有二次开发接口，想接自己的码表或 ESP32 只能干瞪眼；
* 界面是官方定义的，想做一个竖屏仪表、GNSS 天空图或者自己的标定面板，基本不可能。

所以这次的目标很朴素：**自己写一个手机控制面板，直连控制器，读电压 / 电流 / 转速 / 转把电压，并做有限的下发控制。**

项目已经整理到：

## 第一阶段：先把原始协议帧抓下来

控制器用的是 **Nordic UART Service（NUS）** 透传，这个在蓝牙调试助手里一眼就能看出来：

| 用途 | UUID |
|---|---|
| Service | `6e400001-b5a3-f393-e0a9-e50e24dcca9e` |
| 手机 → 控制器 | `6e400002-b5a3-f393-e0a9-e50e24dcca9e`（writeNoResponse） |
| 控制器 → 手机 | `6e400003-b5a3-f393-e0a9-e50e24dcca9e`（notify） |

设备名是 `恒泰普瑞<MAC>`，连上之后大约 **2 Hz** 地往 notify 特征值推数据。每条都是固定 **67 字节**，长这样：

```text
┌──────┬──────┬───────────────┬──────┬──────┐
│ [0:2]│ [2:4]│    [4:65]     │ [65] │ [66] │
├──────┴──────┼───────────────┼──────┼──────┤
│   帧头      │   命令字      │ 载荷 │ 校验 │ 帧尾 │
│ C9 9C / CA AC│ 94 05 / 96 05│ 62 B │ 1 B  │ 0xCC │
└─────────────┴───────────────┴──────┴──────┘
```

一开始用手机蓝牙调试助手和 PC 上的 Python `bleak` 各抓了一轮，把 notify 到的原始十六进制原样存进 `tools/captures/*.json`，再写了一个 Flask 网页小面板实时显示原始帧。比如静止时抓到的仪表帧大概是：

```text
c99c940584844f78829274e4b0b0b4db...e88ed1dbcc
```

这一步的收获是：

* 确认控制器**同一时刻只允许一个中心设备连接**，官方小程序连着的时候，其他 App 是连不上的；
* 确认两种帧在交替发送：`C9 9C 94 05` 和 `CA AC 96 05`；
* 确认每帧都以 `0xCC` 结尾，`[65]` 很像校验和。

但也只是“很像”。载荷里的字节和电压、电流、转速完全对不上，直接按大端读出来的数字非常抽象。

## 第二阶段：ADB + Android 蓝牙抓包

在不知道官方协议的情况下，最直接的办法是：**让官方小程序跑起来，然后把它和控制器之间的蓝牙通信抓下来。**

Android 开发者选项里有一个“**启用蓝牙 HCI 信息收集日志**”。打开之后，手机系统会把蓝牙 HCI 层的数据记录成 `btsnoop_hci.log`。不同 Android 版本路径不太一样，常见有：

```text
/data/misc/bluetooth/logs/btsnoop_hci.log
/sdcard/btsnoop_hci.log
```

如果没有 root，可以用 `adb bugreport` 打一个完整的诊断包，再从里面翻出 `btsnoop_hci.log`：

```bash
adb bugreport bugreport.zip
# 解压后搜索 btsnoop_hci.log 或 btsnoop_hci.log.last
```

把日志拖进 Wireshark，过滤蓝牙 ATT：

```text
btatt
```

或者只看 L2CAP 的 ATT 通道：

```text
btl2cap
```

然后手动对照官方小程序里的操作：

* 连接控制器；
* 看实时数据页面；
* 改一档限速；
* 开关某个功能；
* 断开重连。

在 Wireshark 里就能看到 notify 句柄上每 500 ms 左右来一次 67 字节，以及用户点按钮时从手机发往 write 句柄的写命令。

这个阶段解决的是“**传输行为**”问题：

* 确认官方 App 和小程序确实走的就是 NUS；
* 确认读帧和写帧的长度、速率、触发时机；
* 确认下发命令也是 `C9 9C` 开头，但载荷已经过一层处理，不是肉眼可读的明文。

但 HCI 抓包只能看到“**密文长什么样**”，看不到“**为什么这样加密**”。要还原字段偏移，还得继续往下走。

## 第三阶段：微信小程序逆向解密

官方小程序包 id 是 `wx0ebd16ecb71fee37`，用 PC 微信打开并缓存后，可以得到 `__APP__.wxapkg`。

PC 微信的 wxapkg 不是老式明文包，而是 **V1MMWX** 加密格式。公开的解密流程大致是：

* PBKDF2（salt = `saltiest`）派生密钥；
* AES-CBC（iv = `the iv: 16 bytes`）解密；
* 最后再按 `ord(appid[-2])` 做一次单字节 XOR。

仓库里保留了参考脚本：

[`reverse/pc_wxapkg_decrypt_ref.py`](https://github.com/BI7KHI/htpr-ble-console/blob/main/reverse/pc_wxapkg_decrypt_ref.py)

解密并解包后，关键代码在模块路径 `D:/wook/恒泰/utils/index.js` 里。搜索 `decrypt`、`encryption`、`ab2hex` 这几个函数，整个协议的轮廓就出来了。

### 3.1 最关键的坑：两种帧都要解密

一开始我以为只有 `CA AC` 开头的遥测帧是密文，`C9 9C` 开头的仪表帧是明文。结果电压、转把电压的偏移怎么都对不上，读数全是乱的。

后来在官方小程序的 `ab2hex` 里看到：

```js
n = "c99c" == n.slice(0, 4) || "caac" == n.slice(0, 4)
    ? u(n)   // 对所有 c99c / caac 帧调用 decrypt
    : n;
```

也就是说，**只要帧头是 `C9 9C` 或 `CA AC`，`[4..65]` 都经过了同一套滚动混淆。** 这个结论把之前“字段错位”的问题一次性解释清楚了。

核心解密逻辑：

```python
for o in range(4, 66):
    b = (b - 54) & 0xFF
    b ^= 43
    b = (b - o) & 0xFF
    b ^= 101
    b = (b - o) & 0xFF
```

加密就是逆运算：

```python
for o in range(4, 66):
    b = (b + o) & 0xFF
    b ^= 101
    b = (b + o) & 0xFF
    b ^= 43
    b = (b + 54) & 0xFF
```

字节 `[0:4]` 和 `[66]` 不参与变换。

### 3.2 帧格式与字段映射

解密之后，协议就非常清楚了：

* 校验：`sum(bytes[0..64]) & 0xFF == bytes[65]`；
* 帧尾：`bytes[66] == 0xCC`；
* 多字节字段按**大端**读取。

仪表帧 `C9 9C 94 05`：

| 字段 | 偏移 | 换算 |
|---|---|---|
| 电压 | `BE(63,64)` | `/ 100` → V |
| 转把电压 | `BE(37,38)` | `/ 200` → V |
| 功能设置字 | `BE(44,45)` | 16 bit，其中 bit9 = 强制超速 |
| 高速档限速 | `u8(51)` | motion3 |
| 车型 ID | `u8(48)` | — |

遥测帧 `CA AC 96 05`：

| 字段 | 偏移 | 换算 |
|---|---|---|
| 电流 | `BE(19,20)` | `/ 10` → A |
| 转速原始值 | `BE(21,22)` | `× 20` |
| 显示转速 | 同上 | `floor(rotationalspeed / a)`，本车型 `a = 25` |
| 低速 / 中速档限速 | `u8(11)` / `u8(12)` | motion1 / motion2 |
| 转矩、限流环、运行状态等 | 略 | 见 `tools/PROTOCOL.md` |

官方小程序里一共有 25 处 `writeBLECharacteristicValue`，主要命令包括：

* `c99c0002`：写功能设置、锁车、码表等；
* `c99c0602`：写三档限速、电流、运行模式等；
* OTA 相关命令：`9c9c...`。

命令帧的构造套路也和抓包对上了：

1. 以最近一帧仪表帧为模板，先解密；
2. 改对应字节；
3. 重算 `byte[65]` 校验；
4. 整帧加密后 `writeNoResponse`。

### 3.3 用真实工况验一遍

协议对不对，不能只看代码，还得拿车和万用表验。四组工况的抓包结果如下：

| 状态 | 电压 | 转把电压 | 电流 | 转速 | 校验 |
|---|---|---|---|---|---|
| 静置 | 48.2 V | 0.8 V | 0.0 A | 0 | 100% |
| 低速 | 48.0 V | 1.5 V | 0.1 A | 76 | 100% |
| 高速空载 | 47.5 V | 3.5 V | 1.2–1.3 A | 600–604 | 100% |
| 负载高速 | 47.2 V | 3.5 V | 1.8–13.5 A | 524–600 | 100% |

电压和万用表基本一致，转把电压、电流、转速也都符合直觉。到这里，协议可以说完整还原了。

### 4.3 为什么还要做 GNSS 融合

协议里确实有转速字段，但这个字段有个非常坑的固件行为：

> **松油门滑行时，控制器转速字段恒为 0。**

不是解析错，官方小程序也一样。低速时还会因为霍尔计数窗口太短而间歇性掉零。

所以 App 里做了三速度源融合：

| 模式 | 行为 | 适用 |
|---|---|---|
| `GPS` | 只用 GNSS 真速，无定位时回落转速 | 空旷路段 |
| `融合`（默认） | 驱动中 → 转速；松油门 / 转速掉零 → GNSS | 日常骑行 |
| `转速` | 只用在线标定后的 K 值推算 | 无 GPS / 室内 |

模型是：

```text
speed(km/h) = K · rotRaw
```

用 GPS 真值在线做过原点最小二乘：

```text
K = Σ(gps · raw) / Σ(raw²)
```

采样条件、离群剔除和指数平滑都写在 `app_state.dart` 里。实测标定后 `K/K₀ ≈ 1.16`，说明官方默认的转速系数偏保守。

## 踩坑与经验总结

这次折腾的价值，其实不在“写了一个 App”，而在于把一个闭环走通了。总结几条经验：

1. **先抓包，再逆向，别急着猜字段。**
   没有动态抓包，静态代码里的偏移量很难确认；没有静态逆向，抓到的只是一堆密文。两者必须互证。

2. **传输层和协议层要分开看。**
   NUS 只是“管子”，67 字节帧才是“货物”。先确认 GATT 服务、特征值、读写方向，再谈帧格式。

3. **不要假设“看起来像明文”的帧就是明文。**
   `C9 9C` 帧早期被当成明文，导致电压、转把字段全部错位。后来才发现官方 `ab2hex` 对 `c99c` 和 `caac` 都调用了同一个 `decrypt()`。**这是整个项目最大的一个坑。**

4. **校验和 + 帧尾是最可靠的验伪工具。**
   只要 `sum(bytes[0..64]) & 0xFF == bytes[65]` 且 `bytes[66] == 0xCC`，基本就能确认解密正确。先让校验 100% 通过，再看字段。

5. **一定要有真实物理量对照。**
   万用表读数、转把电压、空载转速、负载电流，都是验证协议正确性的锚点。只靠“数值看起来合理”不够。

6. **协议对，不代表固件行为对。**
   转速在滑行时恒为 0 是控制器固件行为，官方小程序也这样。这种时候只能改软件策略，比如 GNSS 融合和在线标定，而不是怀疑自己的解析代码。

7. **微信小程序版本会影响逆向流程。**
   老版 wxapkg 可能直接解包，新版 V1MMWX 要走 PBKDF2 + AES-CBC + XOR。不同基础库、不同开发者工具版本导出的包也可能有差异，脚本要按实际包格式调整。

8. **单连接限制要提前知道。**
   NUS 模块同一时刻只允许一个中心设备连接。官方小程序连着时，自研 App 会连不上，不是代码问题，也不是蓝牙坏了。先在小程序里点断开。

9. **安全和合规永远是第一位的。**
   只碰自己的设备，只在封闭场地调试，不公开厂商固件，不提供 OTA 能力，不诱导别人上路飙车。**强制超速这个功能，知道它存在就够了，别乱用。**
